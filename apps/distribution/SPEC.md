# @inventarch/distribution

Public language mechanism. The [language reference](LANGUAGE.md) defines vocabulary and evaluation limits. Package exports describe the installed API. Curated agent methods and hosted services are supplied independently.

The [installed system-package API](references/system-package.md) verifies explicit per-system native ownership and exact selected dependencies without executing package code.

Packing (2026-10-09, milestone position-packet plan amendment B7) refuses a release descriptor that names no `distribution`, which the database's descriptor decoder admits for a workspace that releases nothing, as `IA-DIST-CLOSURE-INVALID` as soon as it decodes the descriptor, after it verifies the snapshot's sources and before it admits them, computes the release closure or writes anything; a descriptor that names one packs as before.

The host projection mechanism (`./projection`; 2026-10-09, milestone position-packet task replace-renderers, plan amendment B9) plans and applies the files a caller renders, each carrying the marker the caller passes, at the exact `PROJECTION_PATHS` of each host: `.claude/rules/ia-workspace.md` and `.claude/skills/ia-authoring/SKILL.md` for Claude, `AGENTS.md` and `.agents/skills/ia-authoring/SKILL.md` for Codex, and since milestone generation-binding task host-consumes-generated-set (plan amendments C4, C5 and C12) the generated files `GENERATED_PATHS` names: `.claude/agents/<name>.md` and `.claude/skills/<name>/SKILL.md` for Claude, `.agents/skills/<name>/SKILL.md` for Codex, each a lower-case portable name (`projectionOwnable` is the union). A generated file carries the packet marker and is a planned write owned through the same state; an owned one no render writes any more is removed (an agent through the legacy path below, which deletes only a marked, unedited file); an unmarked or hand-edited file at a generated path is refused, never overwritten or removed; a generated agent is refused (IA-DIST-PATH-UNSAFE) where `.claude/agents` is a link. A generated agent at the path of an owned 1.x steward file replaces it as one update: the legacy pass skips every path an artifact writes, so no plan holds an update and a remove for one path. Besides the caller's marker, the two 1.x markers (`<!-- Generated by tools/projections/generate.ts; edit the cited native records. -->` and `<!-- Generated by ia host; edit the cited native records. -->`) are owned, so a file a 1.x renderer wrote is replaced in place rather than refused. The ownership state format `ia.host-projection-state.v1` is unchanged, and a Claude state may still list `.claude/agents/<name>.md`, for removal only: the planner plans `remove` for each listed one that carries an owned marker and is unedited (a listed one already gone only leaves the state), refuses a listed marked one edited by hand as it refuses any owned file, and lists every other agent file, a listed unmarked one and any the state does not list, marked or not, as `foreign`, which no apply writes or deletes. The final state lists only the files rendered. `observeProjection` reports no drift for a listed steward file that is gone or unmarked. The CLI's `applyHostProjection` is the one caller that applies these plans; the steward-guard registration it retires first is `./guard-registration`'s removal, with the safety checks below.


PR #30 upgrade safety: `assertRetirableGuard` inspects both Claude settings locations and refuses unmatched IA guard groups before a caller deletes steward files, preserving unrelated settings. Guard removal accepts a recorded old-root group only in the fixed released shape and only when the current group matches the recorded bytes; registration and execution retain strict current-root validation. A linked legacy agents directory is foreign and never traversed; listed paths beneath it are left untouched. `legacyProjectionActions` exposes removal/foreign actions independently of active files that an install refresh will render after activation.

Hook groups (`./guard-registration`; 2026-10-11, milestone generation-binding plan amendment C9): `planHookRegistration(root, {cache, hooks} | {remove})`, `planHooksFor(root, expected, hooks)` and `applyHookRegistration(plan, checkpoint?)` plan and apply exactly one PreToolUse group in `.claude/settings.local.json` per hook row `{identity, tools, paths}`: the matcher is `Write|Edit|MultiEdit` whatever the row's tools (which are validated and reported, and which the guard applies to the hook's paths from the record), so the guard's managed-state protection decides every edit tool, and the one handler runs the launcher's guard mode as `guard --root <root> --hook <identity>`, in the derivation the retired steward guard's group used (direct on win32, `/bin/sh` with `FAIL_CLOSED` elsewhere, timeout 10). Nothing authored but the identity, a canonical `system/kind/facet/name` of at most 512 characters, and the tools reaches a group. The groups are owned by exact match against `.ia/distributions/hosts/claude-hooks-<id>.json` (`ia.hook-registration-state.v1`), which also records each hook's registered `paths`, the selection the guard refuses when the hook's record can no longer be read: a plan replaces an owned group whose derivation changed in place, appends a new one, removes one no longer requested, and keeps every other group, key and byte, so a re-plan of the same rows writes nothing and removing the last hook restores the settings byte for byte, except that a container the groups emptied which existed before is written as `[]` or `{}` whatever whitespace it held (a file the first registration created goes again, and containers it created are pruned). It refuses an owned group changed or duplicated by hand, an unmanaged group identical to one it would write, `disableAllHooks` when it would register a group, a consumer root inside the cache, and a malformed or repeated row; an owned group the user deleted only loses its ownership when its hook is no longer requested. Publication holds the host lock and uses the guard's journal, `guard-pending.json` with format `ia.hook-registration-pending.v1`, which every host write already waits on and `recoverGuardRegistration` (`recover-guard`) finishes or rolls back. `assertRetirableGuard` and the retired guard's removal recognize only a guard group that names no `--hook`, so hook groups never block B11's retirement. `readHookRegistration(root)` reads the hook ownership state, `observeHookRegistration(root)` reports each owned group `missing`, `modified` (changed or duplicated) or `foreign` (a guard group naming `--hook` for this root that no state owns), read-only, and `hookGroupDigest(group)` is the SHA-256 a receipt lists for a group. The CLI's projection writer registers and removes the groups (apps/cli SPEC, the generated set).
